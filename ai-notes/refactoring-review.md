### 優先する不具合・保証不足

P1はデータ・ファイルを損なう可能性があり先に扱いたいもの、P2は特定条件での誤動作・利用不能を表す。件数を増やすために同じ原因の入口違いを分割しない。

#### F1 / P1: 生成Sheetを複数回取得すると同じ空白セルが別々に生成される

* 根拠: `CSharp/SpreadsheetAsData.CodeGeneration/WorkbookWrapperComponents.cs:297`、`CSharp/SpreadsheetAsData/Worksheet.cs:13,92,100`、`CSharp/SpreadsheetAsData/Cell.cs:106`。
* 再現: 生成Bookの同じSheetプロパティを2回取得し、両方から未存在の `Z99` を取得する。片方へ101を書いても他方は `BlankValue` のまま。他方へ202を書いて保存すると、再読込時に同一座標が複数存在し `InvalidOperationException` になる。
* 原因: 生成プロパティは都度 `new(this)`、セルキャッシュはWorksheetインスタンスごと。未挿入セルを別々に作り、書込時にも同じ座標を再解決しない。
* 提案: 同一ワークシートのセル状態を共有する責務へ整理する。単なる参照一致の最適化ではなく、二重挿入の防止が必要。異なるラッパー経由の空白セル更新と保存後の読取を一つの回帰テストにする。

#### F2 / P1: Pages出力先のルート保護が末尾の区切り文字で回避される

* 根拠: `scripts/build-github-pages.ps1:11,18,46`。
* 確認済み: スクリプトと同じパス解決・比較式では、ルートそのものは拒否するが、末尾に `/` を付けると拒否しない。`CSharp` や `docs` も出力先として通る。その後は対象ディレクトリを再帰削除する実装である。
* 安全上、削除部分は実行していない。比較式のすり抜けと後続処理を確認したもので、実際にリポジトリを削除して再現したわけではない。
* 提案: 末尾区切りを正規化し、削除してよい生成先の範囲・所有を定義する。ルートとソース領域を失わないテストは一時ディレクトリで行う。既存の「ルートそのものを拒否する」テストだけでは足りない。

#### F3 / P2: 生成BookのOpenで構造検証自体が例外になるとファイルが解放されない

* 根拠: `CSharp/SpreadsheetAsData.CodeGeneration/WorkbookWrapperComponents.cs:124,161`。
* 再現: 生成元のコピーからExcelテーブルの `ref` を除き、生成Bookの `Open(path)` へ渡す。`InvalidDataException` の直後に排他オープンすると `IOException` になる。呼出側へBookは返らないためDisposeできない。
* 原因: 検証条件がfalseになった場合にはDisposeするが、条件評価中の例外を覆っていない。
* 提案: Open成功までの所有権と例外時の解放を一カ所にする。既存の「構造不一致を検出した場合の解放」と、検証中の例外を区別した回帰テストを置く。

#### F4 / P2: 不正なCell.Value代入を拒否する前に数式を消してしまう

* 根拠: `CSharp/SpreadsheetAsData/Cell.cs:73-99`。
* 再現: `TestData/数式セル.xlsx` の数式セルへ `new object()` を代入すると `InvalidCastException`。その後の保存結果には元の数式が残っていない。
* 原因: 型変換の成否が決まる前に、セルの挿入、数式の除去、DataType変更を行う。
* 提案: 単一セルの新しい値を準備できてからXMLへ反映する。拒否した一回の代入で元の値・数式を壊さないことを固定する。範囲・Replace全体のトランザクション仕様へ勝手に広げない。

#### F5 / P2: Table<T>が受け付けた構造体へ読込結果が反映されない

* 根拠: `CSharp/SpreadsheetAsData/Table.Generic.cs:75,88-97`。対照は `WorkbookDataMapper.cs:12-17`。
* 再現: 明示的な引数なしコンストラクターを持つstructを `ReadTable<T>` に使う。属性付きstringプロパティはExcel値ではなく、コンストラクターの初期値 `initial` のまま返る。
* 原因: `PropertyInfo.SetValue(mapped, value)` のたびに値型をボックス化し、元の `mapped` を更新していない。Workbook側は同じ問題を一度だけボックス化して解決している。
* 提案: 受け付ける型なら値を正しく返す。クラス限定にするなら契約を明示して拒否する。共通化候補はこのインスタンス生成・設定の機構であり、異なる変換規則すべてを統合することではない。

#### F6 / P2: 実際の生成ファイル名・nullable設定で警告が発生する

* 状態: 解決済み。`83a0cb4` と `1005d7a` でnullable有効化・生成Dataの初期化を対応。全C#781テスト成功。判断理由は[設計記録](../docs/design.md#生成コードのnullableコンテキスト)を参照。

* 根拠: `WorkbookWrapperComponents.cs:14,260,431`、`CSharp/SpreadsheetAsData.CodeGenerationのテスト/テスト補助/GeneratedSourceCompiler.cs:23-36`。
* 再現: 定義名用の生成ソースを `.g.cs` のファイル名とnullable有効でコンパイルすると、`object?` の箇所に `CS8669`。生成ソース内に明示的なnullableコンテキストがない。該当警告をエラー扱いする利用側でビルドできない。
* 補足: 同じソースを通常ファイルとしてnullable有効で扱うと、範囲・テーブル・dynamicのDataプロパティに `CS8618` も出る。`.g.cs` の場合と同じ警告が出ると混同しない。

#### F10 / P2: セルを書いた後のTable.Rowsが取得時点に取り残される

* 根拠: `CSharp/SpreadsheetAsData/Table.cs:66`、`Table.Generic.cs:16`。

* 原因: Tableは構築時の行一覧を保持する一方、型付きラッパーはその時点で再構築する。範囲外への行追加機能ではなく、既にあるテーブル範囲内のセル編集で発生する。
* 提案: ラッパーごとに違う構造のスナップショットを持つ設計を見直す。F1と同様に、元XML・キャッシュ・公開ビューの整合性を責務として整理する。意図的なスナップショットAPIにする場合は、その契約の明示が別途必要。

#### F11 / P2: 外部Excelのリンク先と生成Bookの既定参照先がずれる

* 根拠: `CSharp/SpreadsheetAsData.Build/GenerateSpreadsheetAsData.cs:66`、`buildTransitive/Marimo.SpreadsheetAsData.Build.targets:14`、`WorkbookWrapperComponents.cs:58`。

#### F12 / P2: 別構成が上書きした生成ソースを古いスタンプで最新扱いする

* 根拠: `GenerateSpreadsheetAsData.cs:76-80,254`。生成ソースはExcelの隣、スタンプはIntermediateOutputPathの下に置かれる。
* 再現: コピーした同じExcelを、異なるNamespace・中間出力先のA→B→Aでタスク実行した。全回成功を返すが、3回目もBの名前空間のまま。生成ソースのハッシュ・更新時刻も2回目から変わらない。元データ・コピーのExcelのハッシュは変わっていない。
* 原因: 3回目のAの入力はA用の古いスタンプと一致するが、共有ソースはBで上書き済み。現在の更新判定は出力の存在しか確認しない。
* 提案: スタンプが、現在使おうとしている出力内容に対応することを確認する。構成別/プロジェクト別の全組合せではなく、共有出力と別スタンプの代表ケースで固定する。

#### F13 / P2・静的確認: パッケージ収集先がビルド出力先の変更に追従しない

* 根拠: `CSharp/SpreadsheetAsData.Package/SpreadsheetAsData.Package.csproj:41`。
* 確認済み: 全部入りパッケージはBuildプロジェクトの `bin/$(Configuration)/net10.0` を固定収集する。MSBuildのBaseOutputPathを変更すると実際のビルド先だけ変わり、収集先は変わらない。
* リスク: 既定場所が空ならタスクDLLを欠く、古い成果物があればそれを梱包する可能性がある。プロパティ評価とコードを確認したもので、出力先変更でのpackは未実行。通常の公開手順で既に欠落しているという指摘ではない。
* 提案: 成果物の実際の出力先をプロジェクト参照から取得するか、公開スクリプトで出力先の契約を制限する。対応前に非標準出力先でのpackをテストとして確認する。

#### F14 / P2: 書式文字を含むテーブル名は生成Dataから対応付けできない

* 根拠: `WorkbookWrapperComponents.cs:221`、`CSharp/SpreadsheetAsData/WorkbookDataMapper.cs:108`。対照は定義名の属性生成 `WorkbookWrapperComponents.cs:273`。
* 再現: `BasicStructure.xlsx` のコピーでテーブル名・displayNameを `sales\u200C_detail`（U+200Cを含む文字列）へ変える。変更前後ともSDK検証0件、生成診断0件、コンパイル成功だが、生成Bookの `Read()` は変更後だけ `InvalidOperationException`。Excel本体での受理は未確認。

### 仕様判断が必要な不整合

#### D1: BlankValueを読み戻して書くとAPIごとに結果が違う

* 確認済み: 範囲の `Values` を配列へ確定して同じ範囲へ代入すると、空白セルが `0 (Double)` になる。一方、型付きTableのobjectプロパティへ読んだ `BlankValue` をそのままReplaceすると `TableMappingException` になる。
* 根拠: `CellRange.cs:69`、`Cell.cs:99`、`TableValueConversion.cs:57`、BlankValueの数値変換。
* 要判断: 数値として使う際の空白→0と、値をそのまま書き戻す際の空白の保存は別の契約である。現在の数値変換テストがあることだけで、書き戻し時の0化も意図した仕様と決めない。
* 提案: object/dynamic・範囲の読込結果をそのまま戻す場合は空白を保つかを決める。採用する場合も、数値への明示的な変換を0とする仕様は独立して維持できる。

#### D2: WorkbookとTableで空白を数値プロパティへ読む規則が異なる

* 確認済み: 数値定義名から生成したdoubleプロパティについて、開いた後に対応セルを空白にして生成Bookの `Read()` を呼ぶと、BlankValueからDoubleへ変換できず `ArgumentException`。Table側の非nullable数値は空白を0として読む。
* 根拠: `WorkbookDataMapper.cs:35,42` と `TableValueConversion`。前回の精査でも変換契約が異なること自体は記録済み。
* 要判断: 意図的な契約差として説明と診断を整えるのか、共通する利用者規則へ揃えるのか。内部実装が似ているだけで共通化せず、利用者に見える規則から決める。

#### D3: 入力Streamをいつまで開いておくかを説明する

* 確認済み: `CopyOnWriteStream.cs:17` はシーク可能な入力を作業コピー生成まで借用し、シーク不可の入力は先にコピーする。`Workbook.cs:52` などはライブラリが入力を閉じないことを説明している。
* 要判断: 所有権が呼出側にあることと、Workbookより先に入力を閉じてもよいことは別である。必要な寿命をXMLコメント・利用例に明記する。
* 全入力をOpen時に即コピーする保証を加えるなら仕様変更になる。現在の実装をリソースリークや不具合とは判定していない。
