# SpreadsheetAsData固有作業指示

この文書は、SpreadsheetAsDataリポジトリに固有の目的、設計、公開準備、周辺運用を定義する。

## プロジェクトの目的

SpreadsheetAsDataを、第三者がビルド、テスト、利用、レビューできるC#/.NETライブラリとして整備する。

機能数を増やすことより、次を優先する。

* 利用側コードの簡潔さ
* 変更箇所の局所化
* 責務分離
* 依存関係の整理
* 低水準APIの抽象化
* 業務的な変換規則の集約
* 公開APIの理解しやすさ
* テスト可能性
* 自動テストによる振る舞いの確認
* READMEから目的、使用方法、制約を理解できること

## 設計と公開API

* 詳細な設計方針は `docs/design.md` を参照する。
* 公開API、依存パッケージ、ビルド構成、永続化形式を変更する前に、理由と影響範囲を確認する。
* 公開APIの変更が必要な場合は、既存利用コード、テスト、サンプルへの影響を確認する。
* SDKや低水準APIの都合を、そのまま公開APIの責務にしない。
* テストのためだけに型やメンバーの公開範囲を広げない。
* 当面はv0系として、API互換性よりも使いやすい設計への修正を優先する。
* 互換性を崩す可能性がある場合は、READMEや設計文書の現在の公開方針と整合するか確認する。

## 仕様・判断と作業の継続

AWS AI-DLCのうち、必要な質問による仕様の明確化、人間による重要な判断、リポジトリへ残した文脈による継続を取り入れる。作業に応じて深さを変え、既存のTDD・レビュー手順を維持する。
参考: [AI-DLCの概要](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)、[作業に応じた工程と深さ](https://aws.amazon.com/blogs/devops/open-sourcing-adaptive-workflows-for-ai-driven-development-life-cycle-ai-dlc/)。全工程の導入や、チャット全文・操作ログの保存は行わない。

記録先は次の既存文書を使い分け、作業状況だけを1ファイルに置く。

| 内容 | 記録先 |
| --- | --- |
| 確定仕様・制約・利用例 | 既存テスト、README、`docs/typed-reading.md`、`docs/public-release-scope.md` の該当箇所 |
| 重要な設計判断・理由・不採用案 | `docs/design.md` の判断記録 |
| 未確定仕様・将来候補 | `docs/roadmap.md` の該当項目。具体化済みの保留仕様は既存方針どおり対象クラスの `Skip` テスト |
| 現在の作業・未完了事項・次回の着手点 | `ai-notes/development-status.md` を上書き更新 |

* 主チャットは開始・再開時に作業状況、Gitのブランチ・差分・関連履歴、今回必要な仕様・判断・テストを確認する。古い作業メモやチェック欄を、現在の実装・検証結果と取り違えない。
* 仕様が不明なら、既存記録を確認してから、利用場面、期待する入出力、制約、既存契約との差など、今回の判断に必要な点だけ質問する。全仕様の洗い出しや、合意済み事項の再確認を毎回行わない。未決定の外部契約が必要になった工程の扱いは既存のTDD規則に従う。
* 記録では「開発者と確定した仕様・判断」「文書・テスト・コード・実行で確認した事実」「AIの提案・推測」「未確認・未決定」を区別し、根拠の文書・テスト名・コミットまたは合意日を添える。コードの挙動だけから開発者の意図を確定しない。食い違いがあれば、どこまで確認できたかを示して質問する。
* 公開API、保存、互換性、責務、依存関係など、後で理由が必要になる判断が確定したら、その作業を区切る前に記録を更新する。決定内容、理由、実際に検討して不採用とした案と理由を数行で残す。理由や判断日を追えない場合は未記録と明示し、後付けしない。変更・撤回した判断は後継の判断と根拠を残す。
* 個々の入力・期待値はテストを参照し、説明文書へ網羅表として写さない。判断記録にはテストだけでは分からない理由を残す。些細な実装選択、全会話の要約、同じ事項の複数文書への転記は不要である。
* 主チャットは中断・終了時に、更新日、目的と現在の工程、完了・未完了、未決定事項への参照、次回最初の作業、検証結果と未実行項目を作業状況へ簡潔に残す。未コミット変更やレビュー・コミット・push待ちも明記する。完了後は待ち状態を解消し、次の製品作業が未選定ならそう書く。過去の進捗ログはGit履歴に任せる。
* 記録と必要範囲の文書検査もレビュー対象へ含め、了承後にコードと同じ作業単位でコミットする。既存のpush規則を適用する。主チャットが記録を管理し、各TDD工程へ全判断履歴・候補一覧・作業メモを持ち込まない。

## C#版とRuby版

* Ruby版のテストは、Ruby側のコードまたはテストデータを変更した場合、またはC#側の変更をRuby側へ同期した場合に実行する。
* C#側だけの変更でRuby側へ反映していない場合は、Ruby版のテストを毎回実行しなくてよい。
* C#版とRuby版で共有するテストデータを変更する場合は、意図した同期かどうかを確認する。
* Ruby版は今回の主対象ではないが、共有テストデータを壊さない。

## テストデータ

* テストデータは、テストの意図が読み取れる最小限の内容にする。
* オールインワンの巨大なExcelファイルで無関係な仕様をまとめて確認しない。
* 既存のテストデータ整理方針がある場合は、それを優先する。
* Excelファイルを開いたことでOpen XML内部の名前空間宣言や属性順序だけが変わることがあるため、値や仕様に関係する差分か確認する。
* Excel保存ノイズらしいバイナリ差分は、明示的な理由なしにコミットしない。

## READMEと公開準備

* READMEと公開準備の観点は `docs/roadmap.md` を参照する。
* READMEには、実装とテストから確認できる内容だけを書く。
* 未実装機能を実装済みのように書かない。
* READMEは、初めて使う人が食いつきやすい順に並べる。
* 高レベル操作を先に示し、必要に応じて低レベルAPIへ進める。
* Visual Studioでの使い始め、CLIでの使い始め、NuGetパッケージ、サンプルデータの導線を保つ。
* デモ動画をREADMEから案内する場合は、GitHub上での実際の挙動を確認する。
* GitHubの通常リンクでダウンロード動作になる動画は、リンク文言にダウンロードと明記する。
* 動画をGitへ直接コミットすると差し替えごとに履歴が太るため、頻繁に更新する動画はGitHub Releasesなどの外部アセット化を検討する。

## APIドキュメントとPages

* C# APIドキュメントは、正規のXMLコメントから生成する。
* APIドキュメント生成は、ローカルで確認できる手順を優先する。
* GitHub Pages公開は、ローカル生成と内容確認の後に行う。
* READMEにPages手順を書く場合は、誰が実行するかではなく、実際に保守できる操作として書く。

## NuGetとVisual Studio連携

* NuGet公開準備では、READMEの記述、パッケージ内容、ローカル確認、実際の公開順序を取り違えない。
* NuGetに公開しないと確認できないVisual Studio連携は、公開前に可能なローカル確認と、公開後の手動確認を分けて扱う。
* Visual Studio上の見え方を変更する場合は、ユーザーの手元で表示確認してから公開作業を進める。
* APIキーや公開用トークンは出力、保存、コミットしない。

## コミット前処理

* コミット前に `scripts/Normalize-ChangedTextFiles.ps1 -IncludeUntracked` を実行し、変更中のテキストファイルの改行コードとBOMを機械的に正規化する。
* 正規化後に差分を再確認する。
* バイナリファイルや動画など、正規化対象外のファイルはサイズと目的を確認してからコミット対象に含める。
