# Red: 利用側から外部契約を決める

`common.md` とこの文書だけを工程指示として読む。Redは失敗テストを作るだけでなく、責務、呼び出し、入力、戻り値、外から見える状態変化を利用側から設計する。実装しやすさや内部アルゴリズムからAPIを逆算しない。

## 調査と設計

今回の要求と確定済み契約を起点に、対象機能、同じドメインオブジェクト、同じ公開境界、類似ユースケース、代表的な呼び出し側、互換性に関係するテストとAPI利用例を検索して読む。最初から全テスト全文を読み込まない。既存テストを現行契約、維持する互換性、旧UI固有、廃止済み、意味未確認に分け、根拠がなければ推測で決めない。

対象の実装本体や内部設計資料は原則として参照しない。共通指示の「既存コードの確認」は、この工程ではAPI宣言と既存の利用例を中心に満たす。確定済み契約を毎回設計し直さず、次の未充足の振る舞いを一件選ぶ。全件のテスト計画や完成形の実装計画を先に確定しない。

テスト中に実際の利用者のcall siteを書く。呼び出しだけで意味が伝わるか、ドメイン上の名前か、引数の意味・順序が分かるか、真偽値や文字列の意味を余計に推測させないか、実装都合の手順を利用者へ要求しないか、既存APIと不必要に異ならないかを読み直す。具体的な問題がある場合だけ代替案を比較する。

期待値は要求と外部契約から決め、現行実装の出力を写さない。テストは何が壊れたら失敗するか分かる粒度にする。同じ振る舞いを明確にする複数assertはよいが、独立した仕様を一件に詰めない。公開APIを示すために必要なら `NotImplementedException` 等の宣言・スタブだけを追加してよい。

仕様変更では、変更したい振る舞いの既存テストを新契約に合わせて修正し、そのRedを確認する。実装に都合よく他の期待値を先に弱めたり、内部変数やprivateメソッドの直接検査のためだけに公開範囲を広げたりしない。新たに明示的な例外を投げる契約は、原則として先にテストで固定する。

## Redの確認

テストを実行し、意図した未実現の振る舞いで失敗することを確認する。API未存在のコンパイル失敗、スタブの失敗、本当に検証したい振る舞いの失敗、環境障害を区別する。意図と違えばテスト・データ・契約を見直し、Greenを始めない。既存実装で正しく通る場合は成功を受け入れ、実装を壊してRedにしない。

本プロジェクトで合意済みの将来観点をまとめて記録する場合は、既存テストとの重複を確認し、理由と解除条件が分かる `Skip` を付ける。`Skip` をGreen対象へ移す前には、対象をユーザーに確認する。未合意の将来仕様を先取りして増やさない。

進行役へ返すのは今回のテストの場所・識別子、失敗結果、確定した契約、新しいAPIの意図だけとする。比較過程や残りのテスト候補はGreenへ渡さない。実装に進まず終了する。
