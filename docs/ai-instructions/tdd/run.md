# 進行役

進行役は、工程担当の起動、成果物の一方向の受け渡し、コミット前の人間レビュー依頼だけを行う。外部APIや内部設計を再審査する統括ではない。

## 開始と起動

要求、作業場所、Gitの未コミット・ステージ済み差分、現在の工程、既定のテスト方法を確認する。既存差分を保全し、同じ作業の続きなら現行の作業場所と成果物から再開する。コンテキスト分離のためにworktreeを作成・再作成しない。

利用可能なら、履歴を継承しない新規担当コンテキストを工程ごとに起動する。この環境のsubagent起動ツールには `fork_context: false` があり、親履歴を渡さず初期指示から開始できる。担当には `docs/ai-instructions/tdd/common.md` と担当工程の文書を読み、さらに委任しないよう指示する。起動後は同じリポジトリの作業場所を見ていることを確認し、異なる場所なら編集を止める。担当を並列実行しない。

同じ工程の失敗修正には、その担当コンテキストへ追加入力してよい。この環境では `send_input`、閉じた担当には `resume_agent` が利用できる。次工程には新しいコンテキストを使う。履歴を継承するforkや、主チャット内の役割切替で代用しない。新規コンテキスト起動が利用できない場合は分離できない旨を報告して停止する。モデルの開始方針が必要なら `models.md` を進行役だけが読む。

## 通常の流れ

Red → Green → ユーザーが未コミット差分を確認 → 了承後にGコミット → Refactor → 実変更があればユーザーが未コミット差分を確認 → 了承後にFコミット → 次のRed。

ユーザーが「Redまで」「Greenまで」「Refactorまで」と範囲を指定したら、指定段階で停止する。コミット・次工程までの許可と読み替えない。

Redには元の要求、確定済みの外部契約、利用場面、既知の互換性制約とプロジェクト参照を渡す。未決定のAPI名や完成形の実装計画を先に決めない。Red担当は必要な既存テスト・利用例を自分で調べる。

Greenには今回のRedテストの場所と識別子、確認済みの失敗、確定した契約、必要な現行コード・関連テスト・テスト方法・必須制約だけを渡す。将来のテスト候補、未採用案、Redの議論、Refactor方針は渡さない。

Greenのテストと終了前確認が終わったら、進行役は未コミット差分の人間レビューを依頼する。追加の意味レビューやテストの再実行を挟まない。ユーザーの了承後にGコミットを作る。既存の `AGENTS.md` が求める対象ファイルとメッセージ案の提示も、この人間レビューに含める。

RefactorにはGのSHA、対象設計領域、現行コード・テスト・契約の参照先、必要な設計・品質規約を渡す。Greenの思考履歴や弁明は渡さない。実変更がなければFコミットも空コミットも作らず、Gを基準として次のRedへ進む。

Redのテストが最初から正しく通るなら、不要なGreen実装はしない。テストのみのコミット要否も従来の人間レビューとコミット承認に従う。

工程担当が未決定の外部契約を報告したら、その工程を止めて判断事項をユーザーへ示す。進行役が新仕様を作って同じGreenへ戻さない。契約を修正した場合は新しいRedとGreenを起動する。依頼範囲の次のRedがなければ終了する。

## この導入で確認した境界

Codexの公式資料では、リポジトリの `AGENTS.md` は各実行で読み込まれ、Skillは名前と説明から選択された時に本文を読み込む。別ファイル化だけでは会話履歴もファイルアクセスも分離しない。現在の起動ツールには親履歴を継承しない指定と、同じ担当への追加入力・再開手段があるが、この運用での編集場所の共有と実際の起動動作は製品作業の初回サイクルで確認する。未確認のまま分離成功とは報告しない。

仕様の確認元: [AGENTS.mdの読込み](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Skillの読込み](https://learn.chatgpt.com/docs/build-skills)、[Codexのsubagent](https://learn.chatgpt.com/docs/agent-configuration/subagents)。
