# Refactor: 外部契約を保って内部設計を整える

`common.md` とこの文書だけを工程指示として読む。GのSHAと対象設計領域を受け取り、現行コード・テスト・契約、設計・命名・品質規約、必要な呼び出し元と先を参照する。Greenの思考履歴や未実装要求の一覧は読まない。

最後に同期したコミットから今回のGまでの差分は、読み直す場所を選ぶ索引として使う。差分だけを現行コードの代用品にしない。同じ設計領域なら担当コンテキストを継続してよいが、版や必要な前提が不明なら現在の正本から新しく組み立てる。

既存コードを含め、同じ意味・同じ変更理由を持つ重複、読みにくい名前や構造、長い処理、責務の混在、不適切な依存関係、不要な変更波及を確認する。見た目が似るだけの処理を無条件に共通化しない。将来機能への備えや形式的な抽象化を追加しない。

振る舞いを保つ小さな変更を重ね、必要なテストを実行する。テスト成功を任意の書換えの同値証明とは扱わない。テストの整理は検証内容を弱めない範囲で行う。抽出したクラスやメソッドに、既存振る舞い以外の入力・例外・保存機能を混ぜない。

不足機能や誤りに気づいたら、この工程で実装しない。現在の整理を妨げなければ、既存テストとの重複を確認した上で、次のRedの `Skip` テスト案として短く残す。外部契約変更が不可欠なら停止する。

改善すべき実在の対象がなければ変更せず、Fコミットも空コミットも作らない。Gを最終基準として進行役へ返す。実変更があれば検証後も未コミットのままユーザーのIDE等での差分確認を待ち、了承後にFコミットを作る。Greenを兼任しない。
