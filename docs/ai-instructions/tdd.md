# TDD作業指示

この文書は、振る舞い追加、仕様変更、不具合修正、リファクタリングに適用する。
C#以外の開発にも共有できる内容として扱う。

## 基本

* TDDは、作業だけでなく考える対象をRed、Green、Refactorへ分け、実行結果からフィードバックを得る手順として扱う。各段階で行わない検討を、単に優先順位が低いだけと解釈して混ぜない。
* 振る舞いの追加や変更、不具合修正では、原則として実装前にテストを追加する。
* Red、Green、Refactorを区別し、「Redまで」「Greenまで」「Refactorまで」と指定された場合はその段階で停止する。

## Redと外部設計

* Redでは、必要な振る舞い、APIの外部設計、使い勝手を考える。実装方法、実装しやすさ、テスト全体の網羅性の検討を同時に持ち込まない。思いついた別の観点は保留し、今の一件に集中する。
* 期待仕様が明確でテストを実行できる場合は、既存テスト・API・データを必要な範囲だけ確認してテストを書き、実行結果から失敗理由を確認する。Redになる見込みを予測・説明するためだけに実装を調査したり、推論へトークンを費やしたりしない。
* Red確認では、失敗したコマンド、失敗理由、意図した失敗かどうかの判断根拠をユーザーへ報告する。
* Red確認が意図した失敗でない場合は、Green実装へ進まず、テスト、仕様、テストデータ、既存設計の確認へ戻る。
* 公開APIを追加または変更する場合は、Red段階のテストをAPI案として扱う。
* APIレビューのためにコンパイルを通す必要がある場合は、`NotImplementedException` などで失敗する最小限の公開APIスタブを追加してよい。

## Skip保留仕様

* API仕様をまとめて検討するためにGreen対象より多いテストを先に書く場合は、保留する仕様テストに理由付きの `Skip` を付ける。
* ユーザーと後で確認することに合意したテスト観点は、既存テストとの重複を確認したうえで、口頭の予定だけにせず `Skip` 付きテストとして残す。既存実装で成功する見込みでも、未レビューなら同様に保留する。未合意の将来仕様を先回りして追加する根拠にはしない。
* `Skip` 理由は、後から読んだ人が、なぜ今は実行対象でないのか、いつ解除するのかを判断できる内容にする。
* `Skip` 理由に単に「未実装」とだけ書かない。
* `Skip` 属性の行から理由が読み取りにくくなる場合は、共通定数化せず文字列を直接書く。
* `Skip` 済み仕様テストは、Green対象にするまで原則として変更しない。
* `Skip` で保留した仕様をGreen対象へ移す場合は、どのテストの `Skip` を外すかをユーザーに確認してから進める。

## Green対象と過剰実装

* Green対象は、一つのテスト、またはユーザーと明示的に合意した小さな仕様のまとまりに限定する。
* Greenでは、現在有効な対象テストを通すための必要最小限の実装を最初から書く。事後チェックで削ることを前提に実装を増やさない。
* Greenでは、内部設計を整えること、アルゴリズムの正当性の検討、ミスがないかの注意深い目視確認を行わない。対象テストを早く通すことに集中し、設計とロジックの検討はRefactorへ分ける。
* Greenの動作確認には自動テストを積極的に使う。成功するかを長く推論するより、対象テストを実行し、結果に基づいて修正する。関連テストや全体テストで既存動作への影響も確認し、実装を最小限にする判断と動作確認を混同しない。
* 必要最小限とは、対象テストが要求する振る舞いを実現することであり、Green対象外の仕様を先取りして固定することではない。
* Green確認後の過剰実装点検は、今回追加したロジックと対象テストとの対応に限定する。対象テストが要求していないロジック（分岐、代入、初期化、後始末など）が含まれ、取り除いても対象テストと既存テストが通る場合は、削除してからGreen完了とする。既存コード全体の点検やアルゴリズム全体の正当性検討へ広げない。
* AIが先の仕様や必要になりそうな実装を推測した場合も、Green対象外なら実装せず、推測として報告する。
* Green中に対象テストとは別の仕様が必要だと分かった場合は、実装せず、理由付きの `Skip` テストまたは確認事項として残す。
* 対象テストが要求していない実装を先に入れ、その後でRedテストを追加して正当化しない。
* 共通処理への実装で、まだ `Skip` している次の仕様テストまで通りそうな場合は、実装前に影響範囲を報告する。
* Green対象外の `Skip` 済み仕様テストやテストデータ全体の整理が必要に見えた場合は、編集前に理由を報告して止まる。
* Green対象を理解するために必要なテストデータ、期待値、補助APIだけを同じ作業単位に含める。
* 予定テストを失敗させ続けるために、公開APIを不自然または不完全な形へ歪めない。
* 同じAPIの正常系と異常系が同じ自然な実装で満たされる場合は、予定テストが通ること自体を避けるための迂回実装をしない。
* 対象テストが要求していない分岐、例外型、エラーメッセージ、戻り値仕様を、自分で判断して追加しない。
* 自分で `throw` を書く例外は仕様として扱い、原則として先にテストで固定する。
* 低水準API、標準ライブラリなどの呼び出し結果として自然に発生する例外まで、すべて明示仕様にする必要はない。

## Refactorとテスト保守

* Green確認後に、外部から観測できる振る舞いを変えずにリファクタリングする。
* 動作確認できるコードを読みやすく整理しながら、内部設計やロジックの妥当性を検討する。小さな変更ごとにテストを実行し、ミスがないという目視の確信で代替しない。
* リファクタリングでクラスやメソッドを抽出・新設する場合も、既存の振る舞いを移すことに限定する。新しいクラスの一般的な役割を理由に、対応する入力、例外処理、保存方法などの新機能を追加しない。既存テストがすべて通ることだけで、新機能の混入がないとは判断しない。
* リファクタリング中に不足機能、ロジックの誤り、未確認の条件へ気づくことは、TDDで次のテストを見つける重要な機会として扱う。既存テストとの重複を確認し、確認すべき振る舞いと期待結果を、理由付きの `Skip` テストとして提案する。リファクタリングへ実装や不具合修正を混ぜず、ユーザーの仕様レビュー後に別のRed→Greenとして進める。
* 既存テストを、実装に都合よく弱めたり削除したりしない。
* テストが誤っている可能性がある場合は、勝手に変更せず報告する。
* 実装済みの仮挙動を仕様として固定するテストを、理由なく追加しない。
* テスト数を増やすこと自体を目的にしない。
* 一つのテストに一つのAssertだけを機械的に強制しない。
* 内部変数やprivateメソッドを直接テストするためだけに設計を歪めない。
* 実装予定のテストが通らない状態を維持することは仕様ではない。
* 将来のテストを通さないために、現在の実装を不自然に読みにくくしない。

## 仕様変更の手順

1. 変更したい振る舞いのテストを新仕様に合わせて修正し、意図したRedを確認する。
2. そのテストを通す必要最小限の実装変更を行う。
3. ほかのテストが失敗した場合は、新仕様によって変更すべき期待か、維持すべき振る舞いの回帰かを精査する。前者は期待を修正してRed→Greenを進め、後者は期待を維持して実装を直す。実装結果に合わせて期待値を追従させない。
4. 変更後も有効な既存テストを含めてすべてGreenにしてから、リファクタリングする。
