# SpreadsheetAsData 設計方針

この文書は、SpreadsheetAsDataの設計判断を記録する。
一時的な作業手順ではなく、実装や公開APIを考えるときの基準を置く。

## 現在の方針

* Excelファイルの内部操作にはOpen XML SDKを使用する方針とする。
* 既存コードを調査してから、Open XML SDKへ置き換える範囲を決める。
* 調査前に既存実装を全面的に書き換えない。
* Open XML SDKの複雑さを利用側から隠蔽する。
* Open XML SDK固有の型を公開APIへなるべく露出させない。
* SDK固有処理は内部実装へ閉じ込める。
* Excelの全機能対応を目指さない。
* 初回公開版で対応するユースケースを固定してから実装する。
* 未対応機能を先回りして実装しない。
* Reactアプリや別のデモアプリを並行して作成しない。
* 実装速度を理由に、テスト、説明、公開準備を省略しない。

## アーキテクチャ

* 公開API、Excel操作の抽象化、Open XML SDK依存処理、型変換、ファイル入出力の責務を分ける。
* ファイル、ワークシート、行、列、セルの責務を曖昧に混在させない。
* セル型、共有文字列、数値、日付、書式の処理を利用側へ押し付けない。
* 業務的な列定義や変換規則を複数箇所へ分散させない。
* 列の追加、削除、順序変更、型変更による修正箇所を局所化する。
* 公開APIは、利用者の意図が読み取れる名前と構造にする。
* SDKの都合を、そのまま公開APIの責務にしない。
* 必要以上に万能なAPIや拡張ポイントを作らない。
* テストのためだけに型やメンバーの公開範囲を広げない。
* 公開APIを変更する前に、既存利用コード、テスト、サンプルへの影響を確認する。
* 公開APIの変更が必要な場合は、変更理由と影響範囲を報告する。

## API互換性

v0.xの再整備中は、[READMEの設計方針](../README.md#設計方針)に従ってAPIを見直す。

公開済みAPIであっても、責務分離、型の一貫性、利用側コードの読みやすさを改善できる場合は、互換性維持より設計整理を優先する。
ただし、API変更は無関係な変更へ混ぜず、変更理由、影響範囲、テスト更新を確認できる単位で行う。

互換性方針自体を変更する場合も、開発者と決めた内容と理由を記録する。

## API仕様テストとTDD

公開APIを考える段階では、実装単位より大きい範囲でテストを書き、API仕様案としてレビューしてよい。
名前、戻り値、利用側コードの見え方、複数機能間の整合性を、実装前に確認するためである。

実装時のTDDは小さい単位で進める。
Green対象は、一つのテスト、またはレビュー済みの小さい仕様のまとまりに限定する。
Green対象ではない仕様テストは、削除やコメントアウトではなく、理由付きの `Skip` として残す。

`Skip` された仕様テストは、実装済み機能ではなく、今後解除してGreenにする保留仕様として扱う。
実装を進めるときは `Skip` を一つずつ外し、失敗理由が意図したものか確認してから最小実装へ進む。
コミット時は、失敗テストがない状態を保つ。

実装中に先の仕様が必要に見えた場合でも、Green対象外であれば実装しない。
保留仕様または確認事項として残し、実装後にRedテストを追加して過剰実装を正当化しない。

先行して書いた仕様テストは、API案や今後の作業メモとして扱う。
Green対象にしていない `Skip` 済み仕様テストは、現在の仮実装や作業中の代表データに合わせて書き換えない。
現在のGreen対象を理解しやすくするために必要なテストデータ、期待値、テスト補助APIだけを同じ作業単位に含めてよい。

実装済みの仮挙動は、それだけでは仕様ではない。
特に名前変換のように未決定の余地が大きい処理では、現在たまたま通っている変換結果を、理由なく仕様テストとして固定しない。

## Open XML SDK

* Open XML SDKのAPI、型、要素構造、保存動作を記憶だけで推測しない。
* 使用するAPIは、参照中のパッケージ、コンパイラ、IDEの型情報、公式資料または実行結果で確認する。
* 現在参照しているOpen XML SDKのバージョンを確認する。
* 異なるバージョンのAPIを混在させない。
* コンパイル成功だけで、生成されたExcelファイルが正しいと判断しない。
* 必要に応じて生成ファイルを再度開き、書き込んだ値を読み取って検証する。
* 共有文字列、インライン文字列、数値、日付、空セル、セル型の違いを考慮する。
* 日付を単なる数値として利用側へ返さない。
* ファイル、ストリーム、SpreadsheetDocumentなどの破棄と保存タイミングを確認する。
* 読み取り専用と書き込み可能な操作を混同しない。
* 不明な既存要素や書式を無条件に削除または再生成しない。
* 既存ファイルを書き換える場合は、対象外のデータや書式への影響を確認する。

## READMEと設計説明

* READMEには、実装とテストから確認できる内容だけを書く。
* 未実装機能を実装済みのように書かない。
* READMEと設計説明を実装終了後まで放置しない。
* APIや責務の変更に応じてREADMEを更新する。
* サンプルは、公開APIの意図が読み取れる最小限のものにする。
* サンプルへ本体と無関係なUIやフレームワークを導入しない。
* Open XML SDKを直接使用した場合との差が分かるようにする。
* 設計図は、主要な責務と依存方向が一枚で分かる程度にする。
* 設計説明と実コードを矛盾させない。

## 判断記録

重要な判断と理由をここへ追記する。個々の入力・期待値はテストを参照する。
以下の過去分は2026-10-19に既存文書・テスト・履歴から整理したものであり、今回あらためて全仕様を開発者に確認したものではない。

### 生成コードのnullableコンテキスト

* 状態: 2026-11-05に開発者と合意。
* 判断と理由: 生成ソースには `#nullable enable` を明示し、nullable注釈とnull安全性のチェックの両方を有効にする。生成コードが既定でnullable無効となるのは古い生成ツールとの互換性のためであり、本ライブラリでは生成側が対応を明示する。
* 不採用案: `#nullable enable annotations` のみを出力すること。CS8669の解消だけには足りるが、生成コード内のnull安全性のチェックも有効にする方針のため採らない。検証で判明した警告は、有効化とは区別して記録・対応する。
* 同日の追加判断: 生成Data型の範囲・テーブルプロパティは `= []` で空コレクションに初期化する。未設定でも非nullableとして扱えるようにし、CS8618を解消する。従来の未初期化によるnullは維持すべき仕様とはしない。nullable化や非null保証のない `!` は採らない。

### 文字列の格納形式と部分書式

* 状態: 2026-11-05に開発者と合意。F7のテスト・実装でGreen確認済み。
* 判断と理由: `Cell.Value` はinlineStrと複数runの共有文字列も通常の文字列として読み、本文を連結する。格納形式や部分書式はデータの読み取りを妨げない。ふりがなは本文へ含めない。
* 書き込み: 値の置き換え後も新しい本文を正しく読み取れることを保証する。セル内の部分書式の保持は要求せず、必ず書式を削除することも契約にしない。

### 保存先と元データの保護

* 状態: 既存方針。`bfe6e93`、`e4fc4c1`、`8705d76` と現在の[保存の説明](../README.md#書き込みと保存)で確認。
* 判断と理由: 元Streamへの `Save()` は拒否する。書き戻し途中の失敗で入力データを部分的に上書きする危険を避けるため。出力には別ファイルまたは別Streamへの `SaveAs` を使う。ファイルの `Save()` は一時ファイルへの出力完了後に置換し、正常終了時点で保存を完了する。
* 不採用案: 元Streamへの直接保存・Dispose時の遅延書き戻し。旧実装から `bfe6e93` で撤去され、Disposeはリソース解放だけにする。元Streamを部分上書きしないという判断が根拠。ファイル置換時の短いロック解除区間と、出力Streamの失敗時の巻き戻しは保証しない。
* 仕様の参照先: [Workbookのテスト](../CSharp/SpreadsheetAsDataのテスト/Workbookのテスト.cs)の `Stream版のSaveは拡張可否によらず元のStreamを変更せずに拒否します`、`DisposeはSaveしていない変更を元のStreamへ書き込みません`、`Saveはブックを閉じる前に元ファイルへ変更を反映します`。

### 工程別TDDと発見した機能不足

* 状態: 既存方針。`bade3f3`、`9718f4e` と[工程別TDDの入口](../.agents/skills/spreadsheet-tdd/SKILL.md)で確認。
* 判断と理由: Red・Green・Refactorの担当コンテキストを分け、各工程に必要な確定情報だけを渡す。Greenへの将来仕様・設計議論の混入と先取り実装を避ける。Refactorで三角測量途中などの明らかな不足を見つけたら、既存契約に基づくSkipテストとして残す。
* 不採用案: 同一会話内で担当名だけを切り替えてコンテキスト分離と呼ぶこと。履歴が分離されないため。発見した機能をその場で追加することも、外部契約を保つRefactorと混同するため採らない。

### 軽量な知識蓄積と再開

* 状態: 2026-10-19の開発者指示に基づき、文書差分のレビュー後に採用。
* 判断と理由: 仕様は既存文書・テスト、判断は本書、未確定事項はロードマップに残し、現在の作業だけを[開発再開メモ](development-status.md)に置く。断続的な作業でも理由と着手点を復元し、文書の二重管理を避ける。
* 採らない構成: AI-DLC全工程の一律導入、別の仕様書一式、判断ごとの独立ファイル、チャット全文の保存。個人OSSで維持する負担が目的に見合わないため。先日予定した独立の候補記録ファイルも作らず、ロードマップへ統合する。
