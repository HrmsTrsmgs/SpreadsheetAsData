# SpreadsheetAsData 設計方針

この文書は、SpreadsheetAsDataの設計判断を記録する。
一時的な作業手順ではなく、実装や公開APIを考えるときの基準を置く。

## 現在の方針

* Excelファイルの内部操作にはOpen XML SDKを使用する方針とする。
* 既存コードを調査してから、Open XML SDKへ置き換える範囲を決める。
* 調査前に既存実装を全面的に書き換えない。
* Open XML SDKの複雑さを利用側から隠蔽する。
* Open XML SDK固有の型を公開APIへなるべく露出させない。
* SDK固有処理は内部実装へ閉じ込める。
* Excelの全機能対応を目指さない。
* 初回公開版で対応するユースケースを固定してから実装する。
* 未対応機能を先回りして実装しない。
* Reactアプリや別のデモアプリを並行して作成しない。
* 実装速度を理由に、テスト、説明、公開準備を省略しない。

## アーキテクチャ

* 公開API、Excel操作の抽象化、Open XML SDK依存処理、型変換、ファイル入出力の責務を分ける。
* ファイル、ワークシート、行、列、セルの責務を曖昧に混在させない。
* セル型、共有文字列、数値、日付、書式の処理を利用側へ押し付けない。
* 業務的な列定義や変換規則を複数箇所へ分散させない。
* 列の追加、削除、順序変更、型変更による修正箇所を局所化する。
* 公開APIは、利用者の意図が読み取れる名前と構造にする。
* SDKの都合を、そのまま公開APIの責務にしない。
* 必要以上に万能なAPIや拡張ポイントを作らない。
* テストのためだけに型やメンバーの公開範囲を広げない。
* 公開APIを変更する前に、既存利用コード、テスト、サンプルへの影響を確認する。
* 公開APIの変更が必要な場合は、変更理由と影響範囲を報告する。

## API互換性

v0.1の再整備中は、まだ利用者が固定されていない前提でAPIを見直す。

公開済みAPIであっても、責務分離、型の一貫性、利用側コードの読みやすさを改善できる場合は、互換性維持より設計整理を優先する。
ただし、API変更は無関係な変更へ混ぜず、変更理由、影響範囲、テスト更新を確認できる単位で行う。

初回公開版または実利用者が発生した後は、破壊的変更の扱いを改めて決める。

## API仕様テストとTDD

公開APIを考える段階では、実装単位より大きい範囲でテストを書き、API仕様案としてレビューすることを許容する。
これは、名前、戻り値、利用側コードの見え方、複数機能間の整合性を、実装に入る前にまとめて確認するためである。

ただし、実装時のTDDは小さい単位で進める。
Green対象ではない仕様テストは、削除やコメントアウトではなく、理由付きの `Skip` として残す。
`Skip` にすることで、テストコードをコンパイル対象に残し、API形状の破綻に気づけるようにする。

コミット時は、失敗テストがない状態を保つ。
`Skip` された仕様テストは、実装済み機能ではなく、今後解除してGreenにする保留仕様として扱う。
実装を進めるときは `Skip` を一つずつ外し、失敗理由が意図したものか確認してから最小実装へ進む。

## Open XML SDK

* Open XML SDKのAPI、型、要素構造、保存動作を記憶だけで推測しない。
* 使用するAPIは、参照中のパッケージ、コンパイラ、IDEの型情報、公式資料または実行結果で確認する。
* 現在参照しているOpen XML SDKのバージョンを確認する。
* 異なるバージョンのAPIを混在させない。
* コンパイル成功だけで、生成されたExcelファイルが正しいと判断しない。
* 必要に応じて生成ファイルを再度開き、書き込んだ値を読み取って検証する。
* 共有文字列、インライン文字列、数値、日付、空セル、セル型の違いを考慮する。
* 日付を単なる数値として利用側へ返さない。
* ファイル、ストリーム、SpreadsheetDocumentなどの破棄と保存タイミングを確認する。
* 読み取り専用と書き込み可能な操作を混同しない。
* 不明な既存要素や書式を無条件に削除または再生成しない。
* 既存ファイルを書き換える場合は、対象外のデータや書式への影響を確認する。

## READMEと設計説明

* READMEには、実装とテストから確認できる内容だけを書く。
* 未実装機能を実装済みのように書かない。
* READMEと設計説明を実装終了後まで放置しない。
* APIや責務の変更に応じてREADMEを更新する。
* サンプルは、公開APIの意図が読み取れる最小限のものにする。
* サンプルへ本体と無関係なUIやフレームワークを導入しない。
* Open XML SDKを直接使用した場合との差が分かるようにする。
* 設計図は、主要な責務と依存方向が一枚で分かる程度にする。
* 設計説明と実コードを矛盾させない。
